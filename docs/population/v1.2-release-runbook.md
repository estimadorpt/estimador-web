# Population v1.2 — release-day runbook (estimador-web)

Window: 4 to 8 December 2026; launch Wednesday 9 December. The site code for the new questions is
already on main (contract: `v1.2-parish-questions.md`), so release day is a data sync and a few
constants. **The bump itself waits for Bernardo's word.** Nothing here is published before it.

## 0. Before you start

- The producer's handoff exists: the v1.2 public bundle (`public_bundle_v1.2.x.json`,
  `experiences_v1.2.x/`, `responses_v1.2.x/`, `scorecard_v1.2.x.json`) with the §2 recipes, the
  census-facts parish responses (`census_attributes_v1.2_parish.parquet` turned into responses by
  the producer, not by the site), the income responses, the release package and `release.json`
  with every file's size, sha256 and licence.
- The producer says whether `household_type` passed the verify-release cross-check (contract §2b).
- Work on a branch; never on main.

## 1. Sync

1. `scripts/sync-population.py`: update `PINNED` (the handoff's sha256 prefixes) and the release
   number; check `GAME_EPOCH` still reads `POPULATION_GAME_EPOCH` = **2026-10-06** and the deck's
   day 0 is still **030857** (the calendar must not move).
2. `./scripts/sync-data.sh population` → `public/data/population/v1.2.x/`.
3. Read the sync's own checks: every parish has every recipe in `recipe_order`, every response
   rebuilds byte for byte.
4. Remove `public/data/population/v1.0.3/` in the same commit. The site reads only
   `POPULATION_DATA_DIR`, and an old v1.0.3 permalink gets the "other release" text without
   fetching anything (checked 18 Nov: `PermalinkResolver` returns before `fetchQueryLookup`, and
   `consultaShellScript` returns when the release differs). Keeping it would cost about 22 MB of the export budget.

**Export budget** (measured 18 Nov from the fixture scaled to 3,092 parishes): v1.2's folder is
about 43 MB. Today's v1.0.3 folder is 22.2 MB: parish files 10.8, the game 9.5 and the lookup 1.3.
v1.2 adds about 5.7 KB per parish (17.8 MB) and about 2.9 MB of lookup entries, and the game is
unchanged. Replacing v1.0.3 adds about 21 MB net: the measured export goes from about 200 MB
(main, 18 Nov) to about 221 MB, over `EXPORT_BUDGET_MB`'s 220 before any Liga growth (Azure's
Free plan limit is 250 MB). Keeping both would put it at about 243 MB.
Release day needs the Standard plan, or a raised `EXPORT_BUDGET_MB` once the plan allows it.

**Update, 19 Nov (launch-plan thread):** web PR 46 brings main's export from 199.9 MB to 137.7 MB
(measured on a build of main + the checks branch + PR 46 + PR 40: 4,710 files, 137.7 MB). It is
held until estimador.pt answers again. Once it is on main, v1.2 lands at about 159 MB, inside the
220 MB budget and the Free plan's 250 MB, so the Standard plan is not needed for the launch.
Re-measure with the real dry-run bundle before release day; if PR 46 is not on main by then, the
paragraph above still applies.

## 2. Constants

- `src/lib/config/population.ts`: `POPULATION_RELEASE`, `POPULATION_PUBLISHED`, the file list in
  `POPULATION_DOWNLOADS.files` (sizes from `release.json`; add the layer files with keys
  `census_facts`, `income`, `vote`, `attitudes` and their licence: EEP vote columns
  `CC BY-NC 4.0`, ESS attitude columns `CC BY-NC-SA 4.0`).

## 4. Checks

1. `npm run og` (regenerates the population card from the new `meta.json`; commit the cards, the
   manifest and `staticwebapp.config.json` together).
2. `npm run check`.
3. Export build from a copy: `git archive HEAD` into a scratch folder, symlink `node_modules`,
   `npm run build` (runs `check:export`: budget, titles).
4. Phone check of one parish page at 360 and 390 px: every section, the Modelado lede, a work card
   with 22 industry bars, the table twins.
5. Push the branch, open the PR; after the preview deploys, `npm run smoke -- --base <preview>`.
6. Ask Bernardo for the go (one card). Merge on his yes; the deploy is the release.

## 5. After

**Notes, 19 Nov (launch-plan thread):**

- **A preview slot must be free before §4 step 5.** The Free plan allows three preview
  environments, and a preview uploaded after its pull request was merged or closed is never
  deleted. On 18 Nov all three were taken: a new pull request's build passed and its preview
  upload was refused ("maximum number of staging environments"). Bernardo frees them in the Azure
  portal (asked on 19 Nov). If none is free on release day, smoke-check the export from a copy
  instead (`git archive HEAD`, `npm run build`, then `node <repo>/scripts/smoke-check.mjs --base
  <a static server on that out/>`): about 111 of 587 lines fail there by design (redirects,
  rewrites and 404 rules a plain server cannot do), and the list must equal main's own.
  The Free plan also allows 500 MB over all environments together (Microsoft's quotas page,
  read 19 Nov). At about 160 MB a copy, production and two previews fit and a third does not,
  so keep at most one other preview alive on release day. That limit has not been seen to
  refuse an upload here; the count of three has.
- **The checks no longer trust "Deployment Complete".** Once the checks change is on main, the
  smoke check exits 3 when the host gives no HTTP answer and names why. A red smoke step after a
  green upload means the host is not serving: look at Azure before re-running anything.
- **The game's calendar is held by a test** (the checks change, `game.test.ts` → `CALENDAR`):
  two digests, of the parish each day plays and of the four on each day's board. After the v1.2
  sync, `npm run check` fails if any of the 3,092 days would play another parish or show another
  board. That replaces the by-hand check of day 0 in §1 step 1. If it fails, the handoff moved
  the calendar (the deck's `daily_order`, or a parish's `census_population` or region): ask the
  producer to keep v1.0.3's, and do not change the digests to pass.
- **Once the release deploy is green, its folder cannot change** (the checks change:
  `scripts/check-published-data.mjs`, a step of the deploy before the build; `npm run
  check:published` runs it by hand). `/data/population/v*` is served immutable for a year, so a
  reader who already holds a parish file never asks for it again. On release day the new folder
  is not on the site yet and passes ("a new release"), and removing `v1.0.3/` whole (§1 step 4)
  passes too. After that, a commit that changes any file of `v1.2.x/` stops the next deploy and
  names the files. The fix is then a new release number (re-sync as v1.2.1, bump
  `POPULATION_RELEASE`), as v1.0.1 to v1.0.3 were on 5 October. So get the data right on the
  preview, before the merge: a preview does not publish a release, and the branch can be re-synced
  as often as needed. Only on Bernardo's word (one card), the stopped run prints a
  `PUBLISHED_DATA_CHANGE_OK` value for that step's `env`, which lets that one change through and
  no later one. The same script fails a folder that does not match its own `manifest.json`.
- **Errata have no place yet.** Limitations known at the release come from the producer (the
  contract's §4 item 9: model card and errata text, which the site quotes). The plan's first
  rule also says that what is found after the launch
  "goes to the errata and to v1.3". Nothing needs building while the list is empty. For the first
  entry, the proposal is a dated list on `/populacao/dados` under the files table (a constant
  beside `SUPERSEDED` in `quality/copy.ts`, not rendered while empty) and the same lines in the
  GitHub release notes. A figure that is wrong where it is shown also gets a note beside it, as
  `RECIPE_CAVEAT.household_type` does for v1.0.3.
- **The week after.** Visits are in PostHog (EU cloud, cookieless); the project has no connector
  for it, so Bernardo reads them. Downloads are the release assets' counts on GitHub
  (`estimadorpt/pt-synthpop`, outside the threads' repository access today). Replies reach him.

## 6. If something goes wrong (added 19 Nov, launch-plan thread)

**Is the release number spent?** It is spent from the moment the live site answers 200 for
`/data/population/v1.2.x/manifest.json`: a reader may already hold the release's files, and keeps
them for a year. `npm run check:published` from the release commit says which it is: "not on the
live site yet, a new release" or "the same as the live site".

**Read the deploy run step by step.**

- Red at the checks, at the published-release step or at the build: nothing was uploaded. The
  site still serves v1.0.3 and the number is not spent. Main is red, though, so nothing else
  deploys either, Liga forecasts included. Fix it on a branch if that takes minutes; otherwise
  revert the merge and try again another day.
- Red at "Build And Deploy": ask the site for the manifest (above) before deciding which case
  this is.
- Upload green and the smoke check exits 3: the host gave no HTTP answer. No commit fixes that.
  Look at Azure and the domain before re-running anything.
- Upload green and the smoke check lists failures: the release is out and a route or an asset
  is wrong. Fix it with a commit that leaves the release folder alone; it deploys as usual.

**A wrong figure found after the deploy is green.** Three answers, cheapest first, each on
Bernardo's word (one card):

1. A note beside the figure, as `RECIPE_CAVEAT.household_type` does for v1.0.3, and a line in
   the errata. Code only, so it deploys as usual.
2. v1.2.1. The folder cannot be edited, and the sync refuses a bundle whose `release_version` is
   not the folder's number, so this needs a re-stamped bundle from the producer and then §1 to
   §4 again. Ask the producer before release day how long a re-stamp takes.
3. Back to v1.0.3: revert the release merge with a pull request. It removes `v1.2.x/` whole and
   restores `v1.0.3/` byte for byte, which the published-release step passes. Links to v1.2.x
   answers then say that the site shows v1.0.3, and the microdata on GitHub stays up until
   Bernardo takes it down.

**After a rollback the number stays spent.** The deploy cannot see this case: the site no longer
serves `v1.2.x/`, so the same folder with other content would pass as a new release, while
whoever read the site in those hours keeps the old files. What comes back is v1.2.1, never the
same number again.

**Before asking for the go (§4 step 6):** the site answers, no other pull request is merging
that morning, `npm run check:published` on the release branch says the new folder is "not on the
live site yet", and Bernardo can be reached for the two hours after the merge.
